# ARCH-001 — Persistence Bootstrap and Canonical Mapping

Version: 1.0  
Status: Frozen  
Decision authority: Enterprise Cognitive Operating Model architecture  
Applies from: CDD-002 onward

## Purpose

This decision record defines how ingestion data reaches the canonical persistence model, how the first ontology actor is represented, how persistence metadata is governed, and which responsibilities belong to the persistence layer. Future CDDs must reference this decision rather than reinterpret these boundaries.

## Architectural precedence

Every implementation layer must follow this order of authority:

```text
Constitution
    ↓
RFCs
    ↓
Logical Model
    ↓
Physical Model
    ↓
EAD-001
    ↓
Persistence
    ↓
CSV Mapping
    ↓
Dataset
```

The canonical model drives implementation; ingestion data adapts to it. A CSV shape must never cause a Physical Model, Logical Model, EAD, Constitution, or RFC change.

## Resolution 1 — EDT-001 is an ingestion dataset

EDT-001 is not the canonical database model. It simulates operational enterprise systems and enters CTEC through an explicit ingestion boundary:

```text
EDT-001 CSV
    │
    ▼
CSV Import Layer
    │
    ▼
DTO
    │
    ▼
Canonical Entity Mapper
    │
    ▼
SQLAlchemy ORM
    │
    ▼
PostgreSQL
```

### Mapping rules

1. Every CSV file maps to one or more existing canonical entities.
2. A CSV filename must never be translated into a new canonical table by convention.
3. CSV columns are external names. Canonical attributes must use names defined by EAD-001 and realized by the frozen Physical Model.
4. A mapping must not introduce an entity, attribute, relationship, or constraint.
5. Semantic construction authorized to a later layer must not be implemented inside persistence.

For example, `Suppliers.csv` does not authorize a `suppliers` table. Its records may participate in mappings to existing constructs such as Enterprise Entity, Institutional Concept, Source Object, Assertion, or Institutional Relationship, but only when the mapping contract and assigned CDD authorize that construction.

An illustrative direct-name mapping uses the real source and canonical names:

| CSV | Column | Canonical entity | Canonical attribute |
| --- | --- | --- | --- |
| `Suppliers.csv` | `Name` | Enterprise Entity | `enterprise_entity_name` |
| `Suppliers.csv` | `Country` | Country | `country_name` |

The complete, governed contract must be recorded in `EDT-001-MAP.md`. Where semantic interpretation is deferred, the mapping document must say so rather than inventing behavior.

## Resolution 2 — `created_by` bootstrap policy

`created_by` always references an Enterprise Entity. Platform users are infrastructure identities; they are not substituted for ontology actors.

The first ontology actor is exactly one bootstrap Enterprise Entity:

| Property | Frozen value |
| --- | --- |
| Canonical name | `ECOM Bootstrap System` |
| Entity type | `System Actor` |
| UUID | Generated by the approved bootstrap process |

The bootstrap entity represents the platform until human actors exist as Enterprise Entities. It is created exactly once, is immutable, and is never deleted.

Future human attribution follows this model:

```text
Human actor
    ↓ represented as
Enterprise Entity
    ↓ referenced by
created_by
```

Infrastructure user records must never be referenced directly by canonical `created_by` attributes.

## Resolution 3 — audit and version metadata

The Logical Model remains a pure expression of business semantics. Generic audit entities, version entities, history entities, or persistence-oriented relationships must not be added to it.

The Physical Model may contain implementation metadata only when that metadata is already defined in EAD-001. No convenience audit columns, soft-delete columns, timestamps, or history structures may be invented by persistence.

Every PostgreSQL column must satisfy exactly one category:

### Category A — Business attribute

The attribute is defined by EAD-001 and realized by the frozen Physical Model.

### Category B — Persistence infrastructure

The element is a primary key, foreign key, index, or constraint already required by the frozen Physical Model. Category B does not authorize additional columns or entities.

Business versioning exists only where the business model defines it. SQL implementation preferences do not create business version semantics.

## Resolution 4 — persistence responsibility

The persistence layer is responsible only for:

- Persisting records
- Retrieving records
- Updating records
- Deleting records
- Enforcing the constraints of the canonical Physical Model
- Managing connections, sessions, transactions, migrations, repositories, and Unit of Work boundaries

The persistence layer remains ignorant of:

- Identity Resolution
- Semantic Resolution
- Assertion construction or interpretation
- Knowledge inference
- Decision Assembly
- Memory
- Reasoning
- Governance decisions
- Learning

Repository implementations contain persistence behavior only. They do not make business decisions.

## Resolution 5 — deterministic seed loading

Seed loading must be deterministic, idempotent, and dependency-aware.

Running the seed command repeatedly against the same canonical schema and EDT-001 version must produce the same canonical database state. The loader must:

- Detect and prevent duplicate loads
- Use stable identity rules for seeded records
- Load only mappings authorized by `EDT-001-MAP.md`
- Verify expected counts
- Produce a summary report
- Be independent of input file ordering
- Avoid random UUID generation outside the approved canonical bootstrap process

Reset behavior must be explicit and must not silently discard data.

## Consequences

- The database is a governed implementation of the ontology, not generic storage.
- Every ORM table must map one-to-one to the frozen Physical Model.
- Every ORM column must trace to EAD-001 and the Physical Model.
- Every canonical foreign key must preserve the relationships and constraints frozen by the authoritative models.
- Every migration must preserve the constitutional and canonical model.
- Dataset convenience never overrides canonical correctness.
- Missing mappings or bootstrap requirements are architecture gaps to report, not invitations to infer.

## Out of scope

This decision does not implement ingestion, identity resolution, semantic resolution, canonical entity construction, assertion interpretation, knowledge inference, decision assembly, memory, reasoning, governance workflows, or learning. Those capabilities require their own CDDs and must remain outside the persistence layer.
