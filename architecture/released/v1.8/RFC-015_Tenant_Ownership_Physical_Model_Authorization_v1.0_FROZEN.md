# RFC-015 — Tenant Ownership Physical Model Authorization

Version: 1.0
Status: FROZEN
Supersedes: — (new authority)
Approval: Product Owner authorization, Increment 3A-0

## Authorization

Authorized by CTEC Product Owner Manoj Nair on 2026-08-13 for Increment 3A-0:
Tenant ownership becomes a first-class physical property of customer-owned source
systems, source objects and enterprise entities. Previously released physical
models remain immutable. The change is delivered through the new physical model
v1.6 and baseline release v1.8.

## Scope

This RFC authorizes exactly two changes to the ECOM Physical Data Model, both
delivered in `architecture/released/v1.8/ECOM_Physical_Data_Model_v1_6.sql`, and
authorizes no other schema, runtime, or capability change.

### 1. Tenant ownership on three canonical tables

`tenant_id VARCHAR(200) NOT NULL` is added to `source_systems`, `source_objects`,
and `enterprise_entities` — the canonical tables that hold per-customer instance
data and were the first surface (the Entity Resolution Steward workspace,
Increment 3A) to disclose that content directly to an authenticated caller. Global
uniqueness on each table's business-key name is replaced with tenant-scoped
uniqueness, and `source_objects.source_system_id`'s foreign key becomes
tenant-qualified (`FOREIGN KEY (tenant_id, source_system_id) REFERENCES
source_systems(tenant_id, source_system_id)`), so a cross-tenant reference is
structurally rejected by PostgreSQL even if application code contains a defect.

`tenant_id` originates only from the trusted authority boundary
(`TrustedPrincipal.tenant_id` → `AuthorityContext.organization_id`), never from an
unrestricted request field, and the runtime fails closed when trusted tenant
context is unavailable. No other canonical table, column, business rule, or
runtime/capability behavior changes. Reference and taxonomy tables (`entity_types`,
`institutional_concepts`, `relationship_types`, `business_domains`, `enterprises`)
remain intentionally unscoped: they hold shared platform vocabulary, not
customer-owned instance data.

### 2. Non-semantic bounded-extension layout normalization

Physical Model v1.5 inherited a defect while accumulating two prior bounded
non-canonical extensions (CDD-012 runtime persistence, CDD-013 application
security audit): the six CDD-012 runtime tables were represented twice — once
verbatim before their own boundary comment, once again after it — and the
CDD-013 audit table sat entirely outside that boundary's scope. Both copies of
every duplicated CDD-012 table were verified column-for-column identical before
this release was generated (see `tools/generate_physical_model_release.py`,
which performs and fails closed on that verification). Physical Model v1.6
corrects only the placement: each of the seven bounded-extension tables (the six
CDD-012 runtime tables and the one CDD-013 audit table) now appears exactly once,
after a single explicit boundary marker
(`-- ---------- BOUNDED NON-CANONICAL EXTENSIONS (CDD-012, CDD-013) ----------`).

This is authorized as a layout correction only. No CDD-012 runtime-persistence or
CDD-013 application-security-audit column, type, default, constraint, index, or
runtime behavior is changed by this release. Both prior releases
(`architecture/released/v1.3/ECOM_Physical_Data_Model_v1_4.sql` and
`architecture/released/v1.4/ECOM_Physical_Data_Model_v1_5.sql`) remain frozen and
unmodified; this correction applies only going forward, to v1.6.

## Non-claims

This RFC does not authorize, and its accompanying tooling does not implement, any
change to CDD-012 runtime-persistence behavior, CDD-013 application-security-audit
behavior, the Supplier Risk API, the Ontology Service API, or any capability
engine other than the Entity Resolution tenant-foundation work of Increment 3A-0.
