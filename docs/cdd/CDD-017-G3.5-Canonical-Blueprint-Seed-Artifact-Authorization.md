## Decision

CDD-017 §17 and §19 defer the exhaustive per-file artifact-authorization record for Gate G's
implementation phases to separate, subsequent, CDD-Template-v2.2-compliant documents, mirroring
CDD-015 §33's exact format — binding: "Implementation MUST NOT proceed against §6's model without
that separate, subsequent artifact-authorization record existing first." This precondition applies
identically to each new implementation phase (already re-applied for G2 and, unchanged, for G3); this
report is that record for G3.5. It follows the same standalone-companion-document precedent already
used for CDD-015 (three merged companions), for CDD-010/CDD-012 (the "-AUTHORIZATION"/"-ALLOWLIST"
companion pattern), and for this CDD's own G2 and G3 companions
(`CDD-017-G2-Persistence-Domain-Artifact-Authorization.md`, merged via PR #78;
`CDD-017-G3-Internal-Application-Service-Artifact-Authorization.md`, merged via PR #80): a standalone
companion document to an already-FROZEN CDD, not an edit to CDD-017 itself, and not a new architecture
baseline.

This report authorizes exactly the artifact scope the Gate G G3.5 Canonical Blueprint Discovery
produced and the Product Owner approved (two decisions, both Option A) — no artifact added, removed,
renamed, or expanded beyond that reviewed scope. It introduces no new architecture: every artifact
below traces to CDD-017's already-authorized §3 ("a future, separately-implemented deterministic seed
populating at least one named canonical Blueprint") and §13 (the seeding-mechanism boundary). G3.5
implements canonical content only, using the already-merged G2 persistence capability and the
already-merged G3 application-service read boundary unchanged — no new persistence artifact, no new
domain artifact, no new application-service artifact, no read API, no frontend, matching CDD-017 §14's
read-surface deferral and the Product Owner's explicit "no implementation" boundary for this governance
phase.

## Approved canonical content (binding, restated for the record)

Per Product Owner Decision 1 (Option A) and Decision 2 (Option A) of the Gate G G3.5 Canonical
Blueprint Discovery Report:

- **Blueprint**: exactly one v1 canonical Blueprint,
  `blueprint_name = "CTEC Semiconductor Supply Chain Blueprint"`, `version_number = 1`,
  `previous_version_id = None`, `lifecycle_state = Active`, `governance_status = Approved`,
  deterministic `blueprint_id` derived via
  `uuid5(BOOTSTRAP_SEED_NAMESPACE, f"{BLUEPRINT_SEED_VERSION}:blueprint:CTEC Semiconductor Supply Chain Blueprint")`,
  matching `OntologySeeder._stable_id()`'s exact derivation convention.
- **ConceptRequirement**: exactly 10, one per already-governed entity type
  (`Supplier`, `Material`, `BOM`, `Product`, `Facility`, `Region`, `Contract`, `Risk Event`,
  `Revenue Exposure`, `Alternate Supplier`), each `obligation = REQUIRED`, each `entity_type_id`
  resolved by name against the
  already-seeded `entity_types` table (never hardcoded, never re-derived independently — see
  Exclusions below).
- **RelationshipRequirement**: exactly 10, one per already-governed relationship type (`supplies`,
  `usedIn`, `defines`, `generatesRevenue`, `locatedIn`, `exposedTo`, `boundBy`, `assembledAt`,
  `coveredBy`, `candidateFor`), each `obligation = REQUIRED`, each `relationship_type_id`/
  `target_entity_type_id` resolved by name against the already-seeded `relationship_types`/
  `entity_types` tables, nested under its source concept's `ConceptRequirement` exactly matching each
  relationship's governed `(source, target)` pairing in `ontology_seed.py::REQUIRED_RELATIONSHIPS`.
- **InformationElementRequirement**: exactly 2 — `element_name = "Supplier Legal Name"`,
  `obligation = REQUIRED`, owned by the `Supplier` `ConceptRequirement`; and
  `element_name = "Risk Event Severity"`, `obligation = CONDITIONAL`, owned by the `Risk Event`
  `ConceptRequirement`. No additional `InformationElementRequirement` is authorized without separate
  Product Owner authorization (Decision 2, binding).

No `EntityType` or `RelationshipType` is created, modified, or re-derived independently by this
report's artifacts — every ontology reference is resolved by name against rows the already-merged
`OntologySeeder` establishes.

## Critical boundaries restated (binding, unchanged from CDD-017)

- **Ontology identity reuse**: every `entity_type_id`/`relationship_type_id` referenced by the seeded
  content resolves to an existing, already-governed `entity_types`/`relationship_types` row by name
  lookup — no parallel ontology, no duplicated concept or relationship identity, no new vocabulary
  (CDD-017 §7). No `EntityType`/`RelationshipType` is created by any artifact in this table.
- **Tenancy**: the seeded Blueprint and all its requirements are global/product-owned. No `tenant_id`
  column, parameter, or seeding logic of any kind (CDD-017 §9).
- **Version model**: exactly one Blueprint row, `version_number = 1`, `previous_version_id = None` —
  no second version is authorized or implied by this report (CDD-017 §6, §8). The version re-parenting
  question the G2 companion left open remains explicitly unresolved and out of scope here.
- **Declarative boundary**: everything authorized here stores declarations only. No runtime
  conformance engine, no tenant conformance scoring, no decision-execution gating, no Entity Resolution
  gating, no Ask CTEC gating, no source-completeness enforcement (CDD-017 §10).
- **Information element boundary**: exactly the 2 `InformationElementRequirement`s named above, each
  `element_name` + `description` + `obligation` only, no type system, no validation rule, no live
  binding to `assertions.predicate` (CDD-017 §11). No additional information element is authorized.
- **Obligation semantics**: `REQUIRED`/`CONDITIONAL`/`OPTIONAL` remains a closed, three-value, purely
  declarative vocabulary (CDD-017 §6, §20) — this report assigns values from that existing closed set
  only.
- **No read API, no UI**: no `api/blueprint/` package, no FastAPI router, no HTTP schema, no frontend
  file, no Blueprint authoring/viewer UI (CDD-017 §14, §16). The already-merged G3
  `BlueprintApplicationService` reads the seeded content unmodified.
- **No runtime behavior change**: no modification to Gate F's DRM/GRM, `runtime/orchestration.py`,
  `runtime/recovery.py`, Ask CTEC's traversal code, Entity Resolution, authentication, or authorization
  (CDD-017 §4, §22).
- **Persistence/domain/application-service untouched**: no modification to `BlueprintRepository`, the
  Blueprint domain model, any ORM model, any migration, or `BlueprintApplicationService`.
