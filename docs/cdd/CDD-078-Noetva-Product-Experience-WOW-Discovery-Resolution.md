**Status:** FROZEN

**Amends:** nothing. Builds on the certified Azure DEV/demo baseline (CDD-067–077, main `4147c8f1d5f2ed7bceddc4c25e43cbf53887bcd1`) and the hardened runbook. Does not reopen either.
**Scope:** the authenticated Noetva frontend's visual/product experience only. No backend, API contract, authorization semantics, Bicep, Docker, Azure, Entra, Cloudflare, or database change is authorized or performed here.

## 1. Executive diagnosis

The current authenticated application is functionally real and truthful (every capability traced to real source this session is genuinely backed by real APIs and, where seeded, real Azure Postgres data) but visually generic: `frontend/app/globals.css` is 460 lines of a plain light-mode admin theme — system `Arial` font stack, no dark mode, no custom typography, no icon system, no animation library, no elevation scale beyond one flat card shadow, exactly 3 shared design-system components (`capability-status-badge`, `empty-state`, `page-header`). Meanwhile `noetva.ai`'s real shipped CSS already contains a mature, on-concept dark-intelligence visual system — deep-navy OKLCH canvas tokens, a real display/body/mono type system (Sora/Manrope/IBM Plex Mono), and named component classes and keyframes (`.observatory-ring`, `.cinematic-grid`, `.layer-plane`, `evidence-travel`, `conflict-ripple`, `node-halo`, `signal-flow`) that are strikingly close to concepts this DR was asked to invent from scratch. **The core diagnosis is not "Noetva lacks a design language" — it's "Noetva has one, and the authenticated product doesn't use it yet."** This materially de-risks the WOW program: the primary work is disciplined extension and application of an existing, real, evidence-based visual system into a dense operational product, not invention from nothing.

A second, load-bearing discovery: Noetva's own internal product docs (`docs/product/NOETVA-CEO-PRODUCT-MASTERY.md`, untracked local files, read in full) already define a truthful-capability vocabulary (`LIVE`/`LIMITED`/`DEMO-SCAFFOLDED`/`DEFERRED`), a real mental model (`CONNECT → RESOLVE → UNDERSTAND → VERIFY → REASON → GOVERN → TRUST`), three explicit "never assume" doctrines ("majority = truth" / "AI recommendation = authorization" / "remediation = resolution" are all rejected), and a scripted 15-minute CEO demo walkthrough that already validates today's finding-detail tab structure and Overview/Command-Center framing as deliberate, not accidental. **Correction to this phase's own governing prompt:** its assumed mental model (`CONNECT→UNDERSTAND→EVALUATE→REASON→GOVERN→IMPROVE→TRUST`) and category tagline ("Ontology-grounded quality intelligence...") differ from the company's own authoritative internal wording in two stage names and the exact tagline. Per this program's own "prefer verified truth over historical assumption" discipline (established throughout the Azure arc), this artifact adopts the real, authoritative internal wording — flagged here explicitly for your confirmation before the next phase treats it as final, since it is foundational to everything downstream.

## 6. Known defect confirmation — invisible input

Root cause reconfirmed directly against `origin/main`: `frontend/app/context/_components/context-lookup.tsx` (lines 87/96) and `frontend/app/quality/evidence-fitness/page.tsx` (lines 93/102) both render bare `<input type="text">` with **no `className` at all**, inside a `<section className="panel">` with no `.form-grid` ancestor. `globals.css`'s Tailwind Preflight import (`@import "tailwindcss"`, line 1) strips all default browser input chrome; only `.form-grid input` (lines 245–253) receives real border/padding. No other bare input was found anywhere else in the app during the fork's full scan — this is a complete, closed list of exactly two occurrences, not a wider systemic pattern requiring speculative additional fixes.

**Systemic fix (design only, not implemented here):** introduce one shared `<TextField>`/`<Input>` primitive in the design system (extending, not replacing, `.form-grid`'s existing visual contract) that every form input in the product uses — including these two — rather than patching two `className`s as a one-off. This closes the defect and prevents recurrence for any future form, which two individual `className` additions would not.

## 7. Information architecture diagnosis

Two real, distinct IA problems, not one: (a) **discoverability** — Supply-Chain Impact is real and correct but reachable only via a 2-click nested path with no top-level surfacing; (b) **route duplication** — `/ontology/explorer` (thin wrapper) and the full `/ontology-studio/*` tree (`ask`, `entity-resolution`, `ontology-modeling`) both exist and appear to serve overlapping purposes, with the primary nav pointing only at the wrapper; `intelligence/ask-ctec` vs. `ontology-studio/ask` may be a similar duplication, not independently confirmed which is canonical. **Resolution direction (design decision, not code change here):** Supply-Chain Impact should be surfaced via an in-page cross-navigation pattern — a real "related intelligence capability" link/card from wherever a supplier-risk-relevant finding or entity is shown (e.g., from the Country-of-Origin finding's own detail view, if a supply-chain-relevant entity is involved) — rather than promoted to a new top-level nav item it does not architecturally deserve on its own (it is a supplier-risk-specific lens, not a ninth peer of Intelligence). The `/ontology-studio` vs `/ontology/explorer` duplication should be resolved by consolidating onto one canonical route tree during WOW-I1 (the foundation phase) as a pure IA cleanup, confirmed with you before executing, since determining which is truly canonical requires a decision only the product owner can make with confidence — this artifact flags it, the next governed phase must resolve it explicitly before touching route structure.

## 14. Reliance/trust direction

## 25. Implementation architecture

Four phases, matching real architectural boundaries actually found during discovery — not the brief's suggested split adopted blindly, but independently arrived at and confirmed to match it:

**WOW-I1 — Foundation + design system + global shell.** Tokens (Section 20), typography import, the `<TextField>` primitive (closing the invisible-input defect systemically), the shell redesign (Section 8), icon-library selection and integration, and the `/ontology-studio` vs `/ontology/explorer` route-duplication resolution. *Why this boundary is real:* every other phase depends on these tokens/primitives existing first; attempting Command Center or OQI work before this would immediately create the "half-new/half-old" regression risk the brief itself warns against (Section 52).

**WOW-I2 — Command Center.** Overview reframe (Section 9), reusing WOW-I1's tokens/shell. *Why real:* Command Center is the first, highest-visibility, lowest-risk surface to prove the new visual system on real data before touching higher-stakes surfaces (auth-adjacent findings/remediation flows).
